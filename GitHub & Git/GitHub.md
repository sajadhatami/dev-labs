### ساختار یک کامیت حرفه‌ای

فرمول کلی نوشتن پیام کامیت به این شکل است:

`type(scope): subject`

- **type (نوع):** ماهیت تغییری که ایجاد کرده‌اید چیست؟
- **scope (محدوده):** کدام بخش از پروژه تغییر کرده است؟ (این مورد اختیاری است اما به شدت پیشنهاد می‌شود)
- **subject (توضیح کوتاه):** توضیح واضح تغییرات به زبان انگلیسی، به طوری که فعل در زمان حال ساده باشد (مثلاً `add` به جای `added`).

### انواع پرکاربرد در بک‌اند (Types)

| **نوع**      | **کاربرد**                                          | **مثال کاربردی**                            |
| ------------ | --------------------------------------------------- | ------------------------------------------- |
| **feat**     | اضافه کردن یک قابلیت یا فیچر جدید                   | ساخت اندپوینت جدید برای دریافت داده         |
| **fix**      | برطرف کردن یک باگ یا خطا                            | حل ارور ۵۰۰ در یک API خاص                   |
| **refactor** | تمیز کردن و بهینه‌سازی کد بدون تغییر در عملکرد      | بازنویسی یک تابع برای کاهش پیچیدگی          |
| **docs**     | اضافه کردن یا ویرایش مستندات                        | آپدیت کردن فایل `README.md`                 |
| **chore**    | کارهای روتین و نگهداری که ربطی به کدهای اصلی ندارند | آپدیت نسخه‌های داخل فایل `requirements.txt` |
### مقایسه کامیت‌های آماتور و حرفه‌ای

- **آماتور:** `add api`
    
- **حرفه‌ای:** `feat(auth): add JWT login endpoint to FastAPI`
    
- **آماتور:** `fix issue`
    
- **حرفه‌ای:** `fix(database): resolve PostgreSQL connection timeout`
    
- **آماتور:** `clean code`
    
- **حرفه‌ای:** `refactor(models): optimize query logic in user model`

### ساختار استاندارد شاخه‌ها (Branches)

- **شاخه `main` (Production):** مقدس‌ترین بخش مخزن شماست. کدی که در این شاخه قرار دارد باید کاملاً پایدار، تست‌شده و آماده استقرار (Deploy) روی سرور باشد (مثلاً همان کدی که نهایتاً روی هاست cPanel بالا می‌آید). شما **هرگز** نباید مستقیماً روی این شاخه کد بنویسید.
    
- **شاخه `develop` (Staging/Integration):** این شاخه برای یکپارچه‌سازی کدهاست. فیچرهای جدید ابتدا در اینجا تجمیع و تست می‌شوند تا مطمئن شویم با هم تداخلی ندارند.
    
- **شاخه‌های `feature/...`:** برای توسعه هر قابلیت جدید، یک شاخه موقت می‌سازید. مثلاً وقتی می‌خواهید سیستم احراز هویت را به پروژه اضافه کنید، یک شاخه به نام `feature/auth-system` می‌سازید.
    
- **شاخه‌های `hotfix/...`:** اگر در نسخه نهایی (`main`) یک باگ اورژانسی پیدا شود که سیستم را مختل کرده است، یک شاخه از `main` می‌گیرید (مثلاً `hotfix/database-crash`)، باگ را سریعاً برطرف می‌کنید و آن را برمی‌گردانید.


ما از ریشه یک شاخه دولوپ میگیریم و برای هر ماژول یک شاخه روی دولوپ میگیریم و در اخر مرج میکنیم رو دولوپ و بعد از رسیدن به مقدار مناسب تست هارو ران میکنیم و مرج میکنیم روی مین .

در هنگام پیدا شدن باگ یک برنچ به نام هات فیکس میگیریم و بعد از ریسولو باگ شاخه رو روی هردو برنچ دولوپ و مین مرج میکنیم.

## اجزای یک Pull Request حرفه‌ای


- **عنوان استاندارد:** عنوان PR نیز باید دقیقاً از همان قانون Conventional Commits که یاد گرفتیم پیروی کند (مثلاً `feat: add user authentication API`).
- **توضیحات (Description) روشن:** باید واضح بنویسید که این کد دقیقاً چه منطقی دارد، چرا به این شکل پیاده‌سازی شده و آیا اجرای آن نیازمند نصب پکیج جدیدی یا تغییر در دیتابیس است یا خیر.
- **اتصال به تسک‌ها (Issue Linking):** اگر این کد برای حل یک باگ ثبت شده نوشته شده است، باید شماره آن را قید کنید. مثلاً با نوشتن عبارت `Fixes #12` در توضیحات، گیت‌هاب به طور خودکار پس از تایید ادغام، آن باگ شماره ۱۲ را می‌بندد.
- **مستندات کمکی:** اگر خروجی یک API را تغییر داده‌اید، قرار دادن یک اسکرین‌شات از پاسخ موفقیت‌آمیز (مثلاً در Postman) به شخصی که کد را بررسی می‌کند کمک بزرگی می‌کند.

## مراحل عملی ثبت PR

- شاخه فرعی خود را با دستور `git push origin branch-name` به گیت‌هاب ارسال کنید.
- وارد صفحه مخزن خود در گیت‌هاب شوید؛ کادری زرد یا سبز رنگ با دکمه `Compare & pull request` ظاهر می‌شود، روی آن کلیک کنید.
- اطمینان حاصل کنید که شاخه مبدأ و مقصد را درست انتخاب کرده‌اید (مثلاً از `feature` به `develop`).
- عنوان و توضیحات را با دقت بنویسید و در صورت نیاز، از بخش Reviewers در سمت راست، هم‌تیمی‌های خود را برای بررسی انتخاب کنید.
- پس از دریافت تاییدیه (Approve) از سوی تیم، دکمه `Merge pull request` را برای ادغام نهایی فشار دهید.

وقتی می‌خواهید یک فیچر جدید بنویسید یا مشکلی را حل کنید، **قبل از اینکه حتی یک خط کد بنویسید**، ابتدا باید یک Issue برای آن ثبت کنید.

### یک Issue حرفه‌ای چه بخش‌هایی دارد؟

- **عنوان واضح:** باید دقیقاً مشخص کند چه چیزی نیاز به توسعه یا اصلاح دارد.
- **بدنه (Body):** توضیحات کاملی از نیازمندی‌ها. در پروژه‌های تیمی، معمولاً قالب‌های آماده‌ای (Issue Templates) وجود دارد که قدم‌به‌قدم از شما می‌پرسد مشکل چیست یا فیچر جدید قرار است چه کار کند.
- **برچسب‌ها (Labels):** برای دسته‌بندی تسک‌ها استفاده می‌شود. برچسب‌های استانداردی مثل `bug` (برای خطاها)، `enhancement` (برای فیچرهای جدید) یا `documentation` (برای مستندات) به پروژه نظم می‌دهند.
- **تخصیص (Assignees):** مشخص می‌کند چه کسی در تیم مسئول انجام این کار است (که در پروژه‌های شخصی، خودت را Assign می‌کنی).

### پیوند جادویی Issue و PR (سناریوی عملی)

فرض کن می‌خواهی در اپلیکیشن فلش‌کارتت، قابلیت محاسبه الگوریتم مرور فاصله‌دار (Spaced Repetition) را به مدل‌های SQLAlchemy اضافه کنی. چرخه کار حرفه‌ای به این شکل است:

۱. در تب Issues یک تسک جدید می‌سازی با عنوان: `Add Spaced Repetition logic to database models` و به آن لیبل `enhancement` می‌دهی. ۲. گیت‌هاب به این Issue یک شماره اختصاص می‌دهد (مثلاً `#5`). ۳. حالا وارد ترمینال می‌شوی، برنچ جدید می‌سازی (`git checkout -b feature/spaced-repetition`) و کدهایت را می‌نویسی. ۴. کدها را Push می‌کنی و یک Pull Request می‌سازی. ۵. **بخش طلایی:** در کادر توضیحاتِ PR خود می‌نویسی: `Closes #5`

با این کار، گیت‌هاب متوجه ارتباط این کد با آن تسک می‌شود. به محض اینکه مدیر فنی کد شما را تایید کند و دکمه Merge زده شود، گیت‌هاب به صورت کاملاً خودکار، آن Issue شماره ۵ را هم می‌بندد (Close می‌کند) و تیک انجام شدنش را می‌زند. این یعنی نهایت نظم و اتوماسیون در مدیریت پروژه.

### ساختار استاندارد بورد پروژه‌ها:

یک بورد حرفه‌ای در بازار کار معمولاً این ستون‌ها را دارد:

- **Backlog / To Do (لیست انتظار):** تمام Issueها و فیچرهایی که تعریف کرده‌اید اما هنوز کار روی آن‌ها شروع نشده است.
- **In Progress (در حال انجام):** تسکی که شما یا هم‌تیمی‌تان یک برنچ جدید برایش ساخته‌اید و در حال کدنویسی آن هستید.
- **In Review (در انتظار بررسی):** وقتی برای کدهایتان Pull Request ثبت می‌کنید، کارت آن تسک باید به این ستون منتقل شود تا مدیر فنی بداند کدی منتظر تایید است.
- **Done (انجام شده):** پس از Merge شدن کدها، تسک به اینجا می‌آید.
